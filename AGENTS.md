## Project boundaries
- Product: RockULA!, tagline Rock Your Spectrum., namespace prefix `RockULA`.
- Original C# implementation of Z80 and Spectrum hardware. Do not wrap or silently port an
  existing emulator. Third-party test vectors and oracle executables need provenance review.
- Core and Formats have no Avalonia, audio-device, filesystem, network, wall-clock or host
  threading dependencies. Hosts own I/O; Formats consumes bytes/streams supplied by hosts.
- One machine is mutated by one owner. CPU, ULA, tape and audio use one integer T-state clock.
  Host rendering and audio delivery do not advance hardware time.
- Initial target: Spectrum 48K, explicitly documented ULA issue/profile. Do not mix 128K,
  Pentagon or other clone timings into its implementation.
- Guest arithmetic wraps intentionally. Parser arithmetic is bounded and validates lengths.
- Firmware, games, secrets, generated binaries, external corpora and user recordings stay out
  of Git. Do not download ROMs automatically or imply that MIT covers third-party assets.
- No speculative generic plugin architecture, distributed services or AI runtime dependency.

## Work protocol
1. Inspect current code, branch and applicable instructions; state the branch and merge target.
2. For substantial work, write/update a focused plan before implementation: goal, files,
   hardware source, failure cases, acceptance commands and limits. Record design changes in an ADR.
3. Create a feature branch from current `main`; use a worktree when isolation is needed.
   The initial repository bootstrap is the explicit exception authorized on `main`.
4. For hardware, parsers and bug fixes, reproduce the behavior with independent expected
   results before changing code. Implement in small testable slices. Do not write a complete
   instruction family before checking its flags and bus events.
5. Diagnose failures by first divergent CPU/bus/raster event, not by changing timing constants
   until a game happens to work.
6. Run relevant checks now and report exact results. If .NET, a display, an oracle or fixture
   is unavailable, state it and leave that validation pending. Never invent a pass.
7. Finish with a reviewable commit/PR as authorized by the task. Do not rewrite shared history,
   force-push, merge unrelated branches or change repository protection.

Optional process skills (brainstorming, writing-plans, test-driven-development,
systematic-debugging, verification-before-completion) may be used when installed. They are not
required external dependencies and their absence does not block work. Follow the protocol above.
Agent profiles are roles, not permission to spawn agents or parallelize overlapping changes.

## Required commands
```sh
dotnet restore RockULA.slnx
dotnet build RockULA.slnx -c Release --no-restore
dotnet test RockULA.slnx -c Release --no-build
dotnet format RockULA.slnx --verify-no-changes --no-restore
```
Use focused test filters during implementation; run the solution checks before completion.
A green scaffold test run is not proof of CPU or game compatibility. UI changes also need an
actual interactive check or a clearly stated pending check.

## Sources and evidence
Read the upstream manual/specification before implementing unfamiliar hardware or a format.
Record version, URL and relevant section in the plan/test comments. Manuals do not fully specify
undocumented Z80 behavior: record the additional measured source and CPU model.
External expected values must not be generated by the implementation under test.
Never weaken tests, skip a failing suite or loosen warnings to manufacture a green result.
